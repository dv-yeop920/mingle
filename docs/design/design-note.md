# 포트폴리오 성능 개선·트러블슈팅 문서 설계안

## 0. 결정 요약

- 최종 산출물은 기존 문서를 수정하지 않고 `docs/resume/portfolio-ai-handoff.md`를 새로 생성한다.
- 이유는 기존 `docs/resume/performance-and-troubleshooting.md`가 별도 목적의 사용자 자료이므로 원문을 보존해야 하며, 다른 AI에게 전달할 완결된 컨텍스트와 증거 규칙은 독립 문서로 분리하는 편이 안전하기 때문이다.
- 이 설계안은 다음 작업자가 최종 문서를 작성하기 위한 명세다. 이 단계에서는 포트폴리오 본문을 수정하지 않는다.
- 문서의 주 독자는 채용 담당자와 기술 면접관이며, 부 독자는 이력서·면접 답변·포트폴리오 글을 생성할 다른 AI다.
- 문서의 핵심 원칙은 `주장보다 증거`, `현재 구조와 당시 구조의 분리`, `비교 가능한 수치만 전후 개선으로 표현`이다.

## 1. 요구사항 정리

### 목적과 독자

최종 문서는 MIXTI에서 실제로 수행한 성능 개선과 장애 해결을 다른 AI가 과장 없이 재가공할 수 있는 근거 문서여야 한다. 독자는 다음 질문에 짧은 시간 안에 답을 얻을 수 있어야 한다.

1. 어떤 사용자·비즈니스 문제가 있었는가?
2. 병목이나 장애의 원인을 어떤 증거로 좁혔는가?
3. 대안 중 왜 현재 해결책을 선택했는가?
4. 무엇이 개선됐고, 그 결과를 어느 수준까지 주장할 수 있는가?
5. 현재 코드에도 남아 있는 구조인가, 과거의 중간 단계인가?
6. 면접에서 추가 질문이 들어오면 어느 원문과 코드를 확인해야 하는가?

### 문서 사용 행동

- 채용 담당자: 핵심 성과와 역할을 빠르게 훑는다.
- 기술 면접관: 문제 재현, 원인 분석, 트레이드오프, 검증 방법을 확인한다.
- 다른 AI: 사례를 선택해 이력서 bullet, 포트폴리오 서술, STAR 답변으로 변환한다.
- 작성자: 숫자나 구현 상태가 바뀌었을 때 근거와 함께 문서를 갱신한다.

### 범위와 부정적 요구사항

- 성능, 안정성, 비용 방어, 데이터 호환성처럼 기술적 판단이 드러나는 사례만 포함한다.
- 기능 목록, 화면 소개, 일반적인 기술 스택 설명을 본문 중심으로 확장하지 않는다.
- 추정치, 서로 다른 측정 도구·시점의 값을 통제된 전후 비교처럼 표현하지 않는다.
- 확인되지 않은 개인 기여 범위, 사용자 수, 비용 절감률, 응답 속도 개선률을 만들지 않는다.
- 과거 구현을 현재 코드인 것처럼 서술하지 않는다.
- 최종 문서를 여러 파일로 분산하거나 새로운 이력서 문서를 병행 생성하지 않는다.

### 엣지 케이스

- 기록 문서와 현재 코드가 충돌하면 `현재 코드`를 현재 상태의 근거로 삼고, 기록은 당시 문제·시행착오의 근거로 제한한다.
- 같은 결과에 여러 최적화가 함께 영향을 줬다면 단일 변경의 성과로 귀속하지 않는다.
- 수치의 측정 조건이 불완전하면 수치를 삭제하기보다 `참고 관측`으로 명시하고 개선율은 계산하지 않는다.
- 과거 데이터 유실처럼 사후 복구가 불가능한 범위는 해결 결과와 분리해 제한사항으로 남긴다.
- 구현을 입증할 코드는 있지만 운영 수치가 없으면 정성적 성과만 주장한다.

## 2. 문서 아키텍처와 읽기 흐름

### 기존 문서와의 관계

`docs/resume/performance-and-troubleshooting.md`는 수정하지 않고 읽기 전용 근거로 사용한다. 최종 단일 핸드오프 문서는 `docs/resume/portfolio-ai-handoff.md`로 새로 만든다.

- 기존 7개 사례의 사실과 출처를 참고하되, 새 문서에 사례별 증거 수준과 현재성 표시를 추가한다.
- 중복되는 `도메인`, `이력서 문장`은 유지할 수 있으나, 각 사례의 기술적 서술보다 앞서지 않게 한다.
- 원문 로그는 최종 문서의 근거 링크로만 사용하고 복사·병합하지 않는다.
- `docs/design/design-note.md`는 구현 계획이며 최종 포트폴리오 산출물이 아니다.

### 최종 정보 구조

1. **한눈에 보기**
   - 프로젝트 한 문단 설명
   - 핵심 성과 3건
   - 기여 범위와 기술 스택
   - 증거 수준 범례 및 현재성 범례
2. **측정 및 주장 원칙**
   - 측정 환경, 비교 가능 조건, RUM과 synthetic 차이
   - 숫자 표현 금지·허용 규칙
3. **대표 사례**
   - 사례마다 동일한 템플릿 사용
4. **보조 사례**
   - 대표 사례보다 압축하되 같은 증거 규칙 적용
5. **횡단적 배움**
   - 성능 측정, 서버/클라이언트 경계, 외부 API 계약, 스키마 진화에서 얻은 원칙
6. **AI 핸드오프 규칙**
   - 재가공 가능 범위, 금지된 추론, 출력별 변환 지침
7. **근거 인덱스**
   - 사례별 원문 문서, 현재 코드, 테스트 위치

### 사례 공통 템플릿

각 사례는 아래 순서를 고정한다.

1. `요약`: 한 문장으로 문제·행동·결과
2. `상태`: 현재 구조인지 과거 구조인지 표시
3. `증거 수준`: 아래 등급과 근거 경로
4. `문제와 사용자 영향`
5. `관측 및 원인 가설`
6. `시도한 접근과 실패/한계`
7. `최종 해결과 선택 이유`
8. `검증 결과`: 정량과 정성 결과를 분리
9. `트레이드오프 및 남은 한계`
10. `면접 포인트`: 예상 꼬리 질문과 답변 근거
11. `재사용 문장`: 이력서용 1문장

### 사례 증거 수준 표시법

각 핵심 주장 뒤 또는 사례 머리말에 다음 등급을 표시한다.

| 등급 | 의미 | 사용할 수 있는 근거 | 표현 원칙 |
|---|---|---|---|
| `E1 · 실측` | 재현 가능한 전후 또는 운영 측정 | 동일 조건 Lighthouse, 네트워크 캡처, RUM, 빌드 산출물 | 조건·도구·시점을 함께 적고 수치 사용 가능 |
| `E2 · 자동 검증` | 동작과 회귀 방지를 코드로 검증 | 단위/통합 테스트, lint, typecheck, build | 기능 보장 범위를 명시하고 성능 수치로 확대하지 않음 |
| `E3 · 구현 확인` | 현재 코드 또는 커밋에서 구조 확인 | 소스 코드, git 이력, 설정 | “구현했다/제거했다” 수준으로 표현 |
| `E4 · 분석 기록` | 당시 진단이나 관측 메모만 존재 | 최적화 로그, 트러블슈팅 문서 | 사실 단정 대신 “관측/분석했다”로 표현 |
| `E0 · 미검증` | 근거를 찾지 못함 | 없음 | 최종 문서에서 제거하거나 검증 필요로 표시 |

한 사례에 여러 등급이 섞이면 주장별로 등급을 나눈다. 예를 들어 폰트 파일 축소는 `E1`, 원인 추론은 `E4`일 수 있다.

### 현재 구조와 과거 구조 구분법

사례마다 다음 상태 중 하나를 제목 아래에 표시한다.

- `CURRENT`: 현재 소스에서 확인되는 운영 구조
- `HISTORICAL`: 문제 발생 당시 또는 중간 리팩터링 구조이며 현재는 대체됨
- `EVOLVED`: 핵심 아이디어는 유지되지만 파일 경계나 구현 방식이 후속 작업으로 변경됨
- `PARTIAL`: 일부 경로나 조건에만 현재 적용됨

과거와 현재가 섞이는 사례는 `당시 구조 → 중간 시도 → 현재 구조` 타임라인으로 쓴다. 현재 구조를 설명할 때는 현재 파일 경로를, 시행착오를 설명할 때는 기록 문서나 커밋을 인용한다. 특히 홈 SSR/PPR 사례는 `src/features/home/design-note.md` 등 후속 설계와 현재 코드를 재확인해 상태를 결정해야 한다. 현재 코드와 다른 중간 단계의 성능 수치는 해당 단계의 결과로만 귀속한다.

## 3. 데이터와 근거 설계

### 사례 우선순위

| 우선순위 | 사례 | 선정 이유 | 현재 확인된 주 근거 |
|---|---|---|---|
| 1 | 웹폰트·Core Web Vitals | 문제 규모, 진단 깊이, 동일 조건 전후 수치가 모두 있음 | `docs/performance/optimization-log.md`, `src/shared/styles/fonts.css` |
| 2 | OpenAI 응답 완전성·비용 방어 | 외부 API 신뢰 경계, O(n²) 비용 상한, 테스트 가능한 안정성 판단이 드러남 | `docs/troubleshooting/openai-result.md`, `docs/design/openai-requirements.md`, `src/app/api/analyze/route.ts`, 관련 테스트 |
| 3 | PPR·Suspense 및 SSR hydration | Next.js/React Query 서버·클라이언트 경계 설계와 시행착오가 풍부함 | `docs/performance/home-ssr.md`, `docs/performance/optimization-log.md`, 현재 홈 코드 재검증 필요 |
| 4 | INP와 클라이언트 실행 비용 | hydration 범위, navigation, animation, layout 비용을 한 흐름에서 설명 가능 | `docs/performance/optimization-log.md`, 관련 현재 코드 |
| 5 | AI 응답·Supabase JSONB 호환 계층 | 스키마 진화와 데이터 유실 방지, 게스트/회원 데이터 소스 통합을 보여줌 | `docs/troubleshooting/openai-result.md`, `src/views/result/lib/normalize-analysis.ts`, 테스트 |
| 6 | 번들·런타임 렌더링 최적화 | 기대와 실측이 달랐던 Turbopack 분석이 좋은 트러블슈팅 사례임 | `docs/performance/bundle-optimization.md`, result view와 hooks |
| 7 | 인증 왕복 중 결과 복원 | route state에 따른 session snapshot 수명과 복원 순서를 보여주는 안정성 사례임 | `src/features/test-flow/design-note.md`, session manager와 관련 테스트 |
| 8 | 웹폰트 변경으로 발생한 OG 500 | 브라우저 최적화가 서버 이미지 런타임을 깨뜨린 회귀와 복구 과정을 보여줌 | `docs/audit/full-2026-08-26.md`, OG·아이콘 generator |
| 9 | Vitest ESM 의존성 충돌 | 직접 원인 수정 뒤 드러난 전이 의존성 문제까지 추적한 사례임 | `docs/audit/full-2026-08-26.md`, `package.json`, `vitest.config.ts` |

대표 사례는 1~3을 우선 배치하고, 4~9는 보조 사례로 유지한다. 진행률·애니메이션 렌더링은 별도 사례를 만들지 않고 4의 INP 사례에 통합한다. 내용이 길어질 경우 사례 수를 늘리기보다 대표 사례의 `가설 → 검증 → 판단` 흐름을 보존한다.

### 근거 의존 관계

```text
원본 측정/문제 기록
  ├─ docs/performance/optimization-log.md
  ├─ docs/performance/home-ssr.md
  ├─ docs/performance/bundle-optimization.md
  └─ docs/troubleshooting/openai-result.md
           ↓ 사실·시점 대조
현재 코드 + 테스트 + git 이력
           ↓ 증거 등급/현재성 부여
docs/resume/portfolio-ai-handoff.md
           ↓ 허용된 범위에서 변환
이력서 bullet / 포트폴리오 / 면접 STAR 답변
```

### 정량 수치 사용 주의

- 전후 개선은 측정 도구, 모드, 네트워크/CPU 조건, 캐시 상태, 배포 버전이 같을 때만 `A → B`, `% 개선`으로 쓴다.
- Lighthouse `simulate`, Chrome `devtools` throttling, PageSpeed Insights, Vercel RUM은 서로 직접 비교하지 않는다.
- 여러 변경이 동시에 배포된 수치는 `전체 최적화 적용 후`로 표현하며 한 기법의 단독 효과로 쓰지 않는다.
- 평균, P75, 단일 관측값을 구분한다. 반복 횟수가 있으면 함께 적는다.
- 예상 효과나 계산치는 실측 결과 표에 넣지 않는다.
- 파일 크기는 저장소 전체, 원본 에셋 합계, 브라우저 전송량(gzip 여부 포함)을 구분한다.
- 운영 비용과 응답 시간은 별도 관측값이 없으면 절감률을 제시하지 않는다.
- `15명·105 pair`처럼 입력 상한에서 계산되는 값은 성능 개선치가 아니라 비용·출력 규모의 상한으로 표현한다.
- 수치마다 가능한 한 `출처 문서/측정 조건/시점/귀속 범위`를 한 세트로 기록한다.

### 문서 상태 관리

문서 작성 흐름은 다음 상태를 따른다.

```text
claim 수집 → 근거 연결 → 현재성 판정 → 수치 비교 가능성 판정
  → E0 제거/보류 → 사례 서술 → AI 핸드오프 검사 → 최종 검증
```

근거가 충돌하면 임의로 합치지 말고 `충돌 발견` 상태로 남긴 뒤 현재 코드, git 이력, 원 측정 기록 순으로 범위를 좁힌다.

## 4. 표현 구조와 접근성

이 작업은 UI 구현이 아니므로 컴포넌트, 폼, Suspense, Activity, 터치 접근성 설계는 적용 대상이 아니다. 대신 Markdown 문서의 탐색성을 다음처럼 보장한다.

- 제목 단계는 `H1 → H2 → H3` 순서를 지키고 사례 간 템플릿을 통일한다.
- 표만 읽어도 핵심 비교가 가능하게 하되, 복잡한 원인과 한계는 본문으로 풀어 쓴다.
- 색상이나 아이콘만으로 증거 수준을 구분하지 않고 `E1` 같은 텍스트 라벨을 사용한다.
- 링크 텍스트는 파일명 또는 근거 내용을 드러내며, `여기` 같은 모호한 표현을 피한다.
- 긴 코드 블록을 복사하지 않고 파일 경로와 핵심 로직만 설명한다.
- 채용 담당자를 위한 요약과 기술 면접관을 위한 상세를 같은 사례 안에서 점진적으로 공개한다.

## 5. 품질, 실패 대응, 운영

### AI 핸드오프 지침

최종 문서에는 다른 AI가 그대로 따를 수 있는 아래 지침을 포함한다.

1. 목적에 따라 `이력서 bullet`, `포트폴리오 상세`, `면접 STAR 답변` 중 출력 형식을 먼저 정한다.
2. 사례의 문제, 직접 수행한 행동, 검증된 결과는 보존하되 문장을 축약할 수 있다.
3. `E1` 수치만 측정 조건과 함께 정량 성과로 강조한다. 서로 다른 측정 체계의 수치를 개선율로 계산하지 않는다.
4. `E2/E3`는 구현·검증 사실로, `E4`는 관측·분석으로 표현한다. `E0` 주장은 사용하지 않는다.
5. `CURRENT/EVOLVED/PARTIAL/HISTORICAL` 표시를 제거하고 현재형으로 평탄화하지 않는다.
6. 원문에 없는 비용 절감액, 트래픽, 팀 규모, 사용자 반응, 담당 비율을 추정하거나 생성하지 않는다.
7. 질문에 필요한 정보가 없으면 그 사실을 밝히고 근거 인덱스의 파일을 추가 확인하도록 요청한다.
8. 기술명 나열보다 `왜 그 선택을 했고 어떤 실패를 피했는지`를 우선한다.
9. 한 bullet에는 가급적 하나의 문제와 하나의 검증 결과만 담는다.
10. 외부 공개 전 비밀키, 내부 URL, 개인 식별 정보가 포함되지 않았는지 확인한다.

### 문서 실패 케이스 매트릭스

| 실패 | 대응 |
|---|---|
| 원문과 현재 코드가 다름 | 상태를 `HISTORICAL` 또는 `EVOLVED`로 바꾸고 양쪽 경로를 표시 |
| 수치 조건을 확인할 수 없음 | 개선율을 제거하고 참고 관측으로 강등 |
| 여러 최적화의 효과가 섞임 | 묶음 성과로 귀속하고 단독 효과 주장 금지 |
| 같은 사례가 여러 문서에 중복됨 | 최종 문서에는 한 번만 쓰고 근거 인덱스에 모든 출처 연결 |
| 테스트가 현재 깨짐 | 과거 통과 기록과 현재 재검증 결과를 구분하고 최신 실패를 숨기지 않음 |
| 문서가 지나치게 길어짐 | 사례를 삭제하기보다 대표/보조 계층과 요약 문장으로 탐색성 확보 |

### 구현 대상 파일

| 파일 | 작업 |
|---|---|
| `docs/resume/portfolio-ai-handoff.md` | 신규 생성. 최종 포트폴리오·AI 핸드오프 문서 |
| `docs/resume/performance-and-troubleshooting.md` | 읽기 전용 근거. 수정하지 않음 |
| `docs/design/design-note.md` | 본 설계안. Plan 단계 산출물로만 추가 |

그 외 소스 코드, 테스트, 원본 성능 로그, `docs/README.md`는 이번 문서 작성 작업에서 수정하지 않는다. 링크 오류나 사실 충돌을 발견하면 최종 문서에 제한사항으로 기록하고 별도 코드 수정으로 확장하지 않는다.

### 구현 순서

사용자 승인 후 다음 작업자는 아래 순서로 진행한다.

1. 기존 문서의 7개 사례에서 주장 단위를 추출하고, 인증 결과 복원·OG 이미지 500·Vitest ESM 사례를 추가 후보로 수집한다.
2. 각 주장에 원문 문서, 현재 코드, 테스트, 필요 시 git 이력을 연결한다.
3. `E0~E4` 증거 등급과 현재성 상태를 부여한다.
4. 비교 불가능한 정량 표현과 단일 변경으로 과대 귀속된 표현을 교정한다.
5. 사례 1~3을 대표 사례, 4~9를 보조 사례로 재구성하고 진행률 최적화는 INP에 통합한다.
6. AI 핸드오프 지침과 근거 인덱스를 추가한다.
7. 아래 검증 계획을 수행하고 결과를 문서 말미 또는 작업 보고에 남긴다.

### 검증 계획

#### 사실성

- 모든 정량 수치를 `rg`로 원본 성능 문서에서 찾아 측정 조건과 일치하는지 대조한다.
- 현재형 구현 주장은 실제 `src/` 코드에서 확인하고, 사라진 구조는 현재형으로 쓰지 않는다.
- OpenAI 응답 검증, 정규화 계층, dynamic mount guard는 관련 테스트 및 현재 코드 위치를 연결한다.
- 필요할 때 `git log`, `git show`로 과거 구조와 커밋 시점을 확인하되 작업 트리는 변경하지 않는다.

#### 구조와 링크

- 문서의 헤딩 계층과 사례 템플릿 일관성을 검사한다.
- 모든 로컬 Markdown 링크와 파일 경로가 존재하는지 검사한다.
- 근거 없는 `E0` 주장, 상태 라벨 없는 사례, 출처 없는 수치가 없는지 검색한다.
- 최종 핸드오프 산출물이 `docs/resume/portfolio-ai-handoff.md` 한 파일로 완결되는지 확인한다.

#### 내용 품질

- 각 대표 사례가 `문제 → 관측 → 가설/시행착오 → 해결 → 검증 → 한계` 흐름을 갖는지 점검한다.
- “개선했다”, “제거했다”, “보장한다” 같은 강한 동사가 증거 수준에 맞는지 검토한다.
- 동일하지 않은 Lighthouse/PSI/RUM 수치를 화살표나 퍼센트로 연결하지 않았는지 확인한다.
- 다른 AI가 원문 없이도 금지된 추론과 허용된 재가공 범위를 이해할 수 있는지 점검한다.

#### 저장소 검증

- 문서만 변경하는 작업이므로 애플리케이션 테스트와 빌드는 기본 검증 대상이 아니다.
- 구현 단계의 `/review`에서는 문서 diff와 사실성 검토를 우선한다.
- `/test`에서는 링크·경로·수치 출처에 대한 정적 검사를 수행한다.
- `/ship` 전에는 사용자 기존 변경과 이번 문서 변경이 분리돼 있는지 확인한다.
