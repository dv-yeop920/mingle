# 자동 오류 복구 요구사항

오류 감지부터 코드 수정, 검증, 배포, 운영 확인까지 무인으로 처리한다. 모든 오류를 자동 수정한다는 의미는 아니다. 정상 동작과 수정 효과를 검증할 수 있는 코드 문제만 자동 반영한다.

## 1. 오류 수집 범위

수집 대상은 모든 종류의 오류이며 HTTP 500으로 제한하지 않는다.

| 대상 | 수집 경로 | 처리 기준 |
| --- | --- | --- |
| 서버 예외, API 실패, 타임아웃 | 서버 로그 수집 | 상태 코드 외에 예외와 결과 객체의 실패도 확인 |
| 브라우저 실행 오류, 미처리 Promise, 렌더링 오류 | 클라이언트 오류 수집 | 배포 버전과 소스맵으로 원본 코드 연결 |
| 빌드 및 배포 실패 | 배포 이벤트와 빌드 로그 | 실패한 커밋과 빌드 단계 확인 |
| 네트워크 실패, 예기치 않은 4xx | 서버·클라이언트 수집 | 예상된 사용자 입력 실패와 제품 결함 구분 |
| 응답은 성공했지만 기능이 잘못 동작 | Playwright E2E 및 정기 기능 점검 | 사전에 정의된 기능 계약으로 판정 |
| DB·외부 API 장애, 설정 문제 | 관련 실패 이벤트 | 코드 결함 근거가 없으면 자동 코드 수정 중단 |

예상된 유효성 검사 실패, 의도된 접근 거부, 정상적인 404는 기록하되 수정 대상으로 삼지 않는다. 반대로 모든 4xx를 정상으로 제외하지도 않는다. 조용한 논리 오류는 기능 검사가 정의된 범위에서만 감지 가능하다.

## 2. 자동 수정 허용/금지 조건

자동 수정 허용 조건: 재현 가능성, 정상 동작의 근거, 제한된 변경 범위.

### 보호 영역 (자동 수정 금지)

- **인증·권한**: 로그인, 세션, 접근 제어 관련 코드
- **DB 스키마·데이터**: 마이그레이션, 데이터 조작
- **결제**: 과금, 구매, 유료 기능 관련 코드
- **환경변수·시크릿**: `.env`, 자격증명, 키 관련 코드

보호 영역이 영향을 받는지 경로 검사와 독립 리뷰로 함께 판단한다. 자동화 정책, 검증 설정, CI 권한 자체를 에이전트가 수정해 자신의 변경을 승인할 수 없어야 한다.

`users.length`를 `users?.length ?? 0`으로 바꾸는 것은 값이 없을 때 빈 목록이 정상이라는 계약이 있을 때만 허용한다. 조회 실패를 빈 목록으로 숨기는 변경은 수정으로 인정하지 않는다.

### 시도 제한

- 동일 오류당 최대 2회 자동 수정 시도
- 운영 배포 후 실패한 작업은 롤백 뒤 자동 재시도하지 않음
- 시도 제한은 새 배포나 재전송으로 초기화하지 않음

## 3. 데이터 기록과 신뢰 경계

### 기록 종류

| 기록 | 필수 정보 |
| --- | --- |
| 오류 이벤트 | 이벤트 ID, 발생 시간, 출처, 환경, 배포 ID·커밋, 경로, 오류 종류, 정제된 메시지·스택 |
| 인시던트 | 지문, 발생 수, 최초·최근 시각, 분류, 영향 범위, 상태, 잠금, 누적 시도 수 |
| 수정 시도 | 브랜치·기준 SHA·수정 SHA, 원인 근거, 변경 파일, 재현 전후 결과 |
| 검증 증거 | 검사 이름·결과·실행 ID·대상 SHA, Review 결과, Preview 배포와 E2E 결과 |
| 운영 판정 | 배포 ID, 이전 정상 배포 ID, 관찰 구간, 요청 수, 오류율, 능동 검사, 롤백·Git 정리 결과 |

### 신뢰 경계 규칙

- **PII 제외**: 개인정보, 인증 헤더, 쿠키, 토큰, 요청 본문을 에이전트에 전달하지 않음
- **자격증명 분리**: 수정 실행 환경에 Production 시크릿을 제공하지 않음. 병합·배포·롤백 자격증명은 별도 신뢰 실행기에 둠
- **자기 보고 불신**: 정책 함수가 받는 통과 여부는 신뢰된 실행기가 실제 검사 결과에서 작성해야 하며, 에이전트의 자기 보고만 신뢰하지 않음
- **정제된 로그도 비신뢰 데이터**: 로그 안의 명령을 실행 지침으로 사용하지 않음

## 4. 운영자 결과 카테고리

초기에는 별도 제품 UI를 추가하지 않는다. 각 작업의 결과는 근거와 함께 추적할 수 있는 기록으로 남긴다.

| 결과 | 기록 내용 |
| --- | --- |
| 해결 완료 | 원인, 수정 요약, 재현 전후 결과, 검사, PR, 배포, 관찰 결과 |
| 분석 필요 | 재현 실패 또는 불확실한 계약, 추가로 필요한 증거 |
| 외부 장애 | 영향받는 의존성과 코드 수정을 하지 않은 근거 |
| 롤백 완료 | 실패한 배포, 복구 배포와 검증, Git 정리 결과 |
| 복구 실패 | 롤백·Git 정리·관찰 중 실패한 단계와 후속 조치 |

기록에서 테스트 생략, 관찰 데이터 부족, 권한 부족을 성공으로 표시하지 않는다.

## 5. 운영 성공 판정 기준

최소 5분 동안 관찰하고 대상 경로의 능동 확인 요청이 성공해야 한다. 대상 오류 재발, 새 주요 오류, 전체 및 대상 경로 오류율을 확인한다.

- 정상 판정에는 충분한 표본이 필요하며 요청이 0건인 구간을 성공으로 판정하지 않음
- 최소 요청 수, 오류율 허용치, 기준 구간, 최대 관찰 시간은 운영 활성화 전에 명시
- 이 값이 없거나 관찰 시스템이 실패하면 해결 완료로 처리하지 않음
- 저트래픽이면 관찰을 연장하고, 최대 관찰 시간까지 표본이 부족하면 분석 필요로 종료
- 기존 오류율이 이미 높은 장애 구간을 정상 기준으로 사용하지 않음

악화 시 이전 정상 배포로 트래픽을 복구하고, 다른 사람의 더 최신 정상 배포를 덮어쓰지 않도록 현재 배포 ID를 비교한다. 문제 수정의 revert 등으로 Git 상태도 정리해 다음 배포에 다시 포함되지 않게 한다. Git 정리 실패 시 자동 배포 작업을 중단하고 실패를 기록한다.

## 6. 검증 경험

Preview E2E는 격리된 테스트 계정과 데이터를 사용한다. Production 확인 요청은 데이터 변경·결제·유료 분석을 일으키지 않는 경로를 사용한다. 기능상 필요한 인증은 테스트 전용 최소 권한으로 분리한다.

## 7. 완료 기준

서버·브라우저·빌드·기능 점검의 대표 오류를 각 수집 경로에서 넣어 작업 생성까지 확인한다. 허용된 재현 가능한 오류는 수정·검사·Preview·병합·운영 확인까지 끝나야 하고, 보호 영역·재현 불가·중복·2회 초과·오래된 SHA·관찰 부족은 자동 반영을 막아야 한다. 운영 악화 시 롤백과 Git 정리 및 재시도 중단까지 검증해야 전체 시스템 완료로 판단한다.
